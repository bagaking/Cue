## Pass Question

What evidence-backed architecture and product boundaries should Cue adopt for sync portability, .cue/.cue.md compatibility, and explicit screenshot attachments?

## Source Classes To Seek
- Copper launch/update posts, reply threads, and public owner responses.
- Public GitHub issues, forum threads, and reviews from comparable local-first
  capture or notes tools.
- Primary format specifications and owner documentation for package-based
  Markdown interoperability.
- Apple developer documentation and audited macOS screenshot implementations.

## Planned Tracks
- `tracks/copper-discussion.md` — collect Copper owner posts and attributable public user replies
- `tracks/adjacent-demand.md` — collect comparable-tool user evidence for sync mobile attachments conflicts offline and privacy
- `tracks/format-architecture.md` — compare package and Markdown interoperability contracts and derive one-way .cue.md semantics
- `tracks/capture-platform.md` — verify Apple-native region/window capture APIs and audited open-source implementation patterns

## Budget Or Stop Rule

At most eight retained sources per track. Stop earlier when the evidence
threshold is met and the next source would not change a requirement, confidence
level, or architecture limitation. Record access gaps explicitly.

## Merge Expectations
- Track workers own only their track file plus assigned source cards and
  summaries. The main agent alone writes claims, insights, proposal decisions,
  Tracker state, or product code.
